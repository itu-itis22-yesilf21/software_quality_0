# Phase 2 / Step 2 — Prompt Design Log

This log captures the two prompts that will be sent to **LLM A (GPT-5.5)**
and **LLM B (Gemini 3.1 Pro)** in Step 3 to generate the `BookScan` class.
The same two prompts go to both LLMs so the four resulting variants are
directly comparable (Step 11).

The assignment text (Phase 2, "Class Generation") says:

> Create a Java class called *BookScan* using LLM agents. The primary
> purpose of this class is to determine how many times words of a given
> length appear in a text and in which lines they appear. Make sure the
> class contains three methods related with the tasks, namely
> #18 "substring", #23 "string length", #27 "upper-lower case" from the
> given dataset in Phase 1.

The three HumanEval method signatures we must keep are therefore:

- `Java/18` → `public int howManyTimes(String string, String substring)`
- `Java/23` → `public int strlen(String string)`
- `Java/27` → `public String flipCase(String string)`

Phase 2 also explicitly requires:

> Compare the code generated by using the prompts unmodified&combined and
> the code generated by using the prompts edited&combined by you. Explain
> how you have approached improving the prompt.

So we need **two prompts**, not one.

---

## Variant 1 — Unmodified + Combined prompt

**Intent.** Concatenate the three HumanEval prompts (Java/18, Java/23,
Java/27) verbatim — exactly as they appear in `humaneval_java.jsonl` —
and add only the minimal text required by the Phase 2 brief: build a
class called `BookScan` that uses those three methods to count
length-`k` words per line. No additional contract, no tokenisation rules,
no edge-case guidance. This variant is the baseline: it shows what the
LLM does when handed the dataset prompts as-is.

**Full prompt to send (begin → end):**

```text
You will write a single Java file called BookScan.java.

The class BookScan must contain three methods whose specifications are
copied verbatim from the HumanEval-Java dataset below. Do not change the
method signatures, the Javadoc, or the example behaviour. Place all three
methods as instance methods of BookScan.

--- HumanEval Java/18 ---
import java.util.*;
import java.lang.*;

class Solution {
    /**
    Find how many times a given substring can be found in the original string. Count overlaping cases.
    >>> howManyTimes("", "a")
    0
    >>> howManyTimes("aaa", "a")
    3
    >>> howManyTimes("aaaa", "aa")
    3
     */
    public int howManyTimes(String string, String substring) {

--- HumanEval Java/23 ---
import java.util.*;
import java.lang.*;

class Solution {
    /**
    Return length of given string
    >>> strlen("")
    0
    >>> strlen("abc")
    3
     */
    public int strlen(String string) {

--- HumanEval Java/27 ---
import java.util.*;
import java.lang.*;

class Solution {
    /**
    For a given string, flip lowercase characters to uppercase and uppercase to lowercase.
    >>> flipCase("Hello")
    "hELLO"
     */
    public String flipCase(String string) {

--- BookScan responsibility ---
In addition to the three methods above, BookScan must provide a public
method that, given a text and a target word length, determines how many
times each word of that length appears in the text and in which lines it
appears. The method must use howManyTimes, strlen, and flipCase from the
same class.

Return ONLY the contents of BookScan.java, with the @Authors header
already present at the very top of the file (exact text, three lines):

/*@Authors
Student Names: <Kutay Murat Kasman><Furkan Bilal Yeşil><Ahmet Çavdar>
Student IDs:<150210062><10210041><150210059>*/
```

**Rationale (why this prompt is the "unmodified" baseline).**

1. The three HumanEval prompt blocks are pasted in **exactly** as they
   appear in `humaneval_java.jsonl`. No re-wording, no extra examples,
   no boundary clarifications. This matches the "do not change the
   prompt description" rule from Phase 1's code-generation step
   ([Phase 1 brief](../../2526_BLG_475E_Project.pdf)) and lets us
   measure prompt-induced quality the same way as Phase 1.
2. The BookScan responsibility paragraph is a single sentence
   paraphrased from the assignment brief. It deliberately leaves
   tokenisation, case sensitivity, line numbering, and the output type
   **undefined** — this is the variable we want to study.
3. We require the `@Authors` header up-front so the file is
   submission-ready and so any header drift is the model's fault, not
   ours.

**Predicted weaknesses we expect to observe in the output:**

- Inconsistent tokenisation (split on `\\s+` vs `[^A-Za-z]+`).
- Ambiguous line numbering (0-based vs 1-based).
- Case handling either ignored or done without using `flipCase` (the
  three methods get pasted in but the BookScan logic re-implements them).
- Output shape varies wildly: `Map<String,Integer>`, `Map<String,List<Integer>>`,
  a custom record, or printed to stdout.
- `howManyTimes` may be used only inside an unused helper; the model may
  count words by direct `equals()` instead.

These predicted weaknesses are exactly what the **edited** prompt below
fixes, and the Step 11 comparison table will record whether they
actually showed up.

## Variant 2 — Edited + Combined prompt

**Intent.** Same three HumanEval methods, but with an explicit
integration contract: API shape, tokenisation rule, case rule, line
numbering, output type, and edge-case behaviour. The three methods
are required to be **real internal callees**, not decoration. Errors
in the integration (e.g. case-sensitive matching) become detectable
because the spec pins the expected behaviour.

**Full prompt to send (begin → end):**

```text
You will write a single Java file called BookScan.java for a course
project on software quality and testing. Follow the spec below exactly.

============================================================
PART A — Three required helper methods (HumanEval Java/18, 23, 27)
============================================================

These three methods MUST be public instance methods of BookScan with
the exact signatures shown. Their bodies must implement the behaviour
described in their Javadoc. The integration method in Part B MUST
delegate to these helpers; do not inline equivalent logic.

(1) Java/18 — substring counting (overlapping):
    /**
    Find how many times a given substring can be found in the original string.
    Count overlapping cases.
      howManyTimes("", "a")     -> 0
      howManyTimes("aaa", "a")  -> 3
      howManyTimes("aaaa", "aa") -> 3
     */
    public int howManyTimes(String string, String substring);

(2) Java/23 — string length:
    /**
    Return the length of the given string.
      strlen("")    -> 0
      strlen("abc") -> 3
     */
    public int strlen(String string);

(3) Java/27 — flip case of every letter:
    /**
    Flip every lowercase letter to uppercase and every uppercase letter
    to lowercase. Non-letter characters are unchanged.
      flipCase("Hello") -> "hELLO"
     */
    public String flipCase(String string);

============================================================
PART B — Integration method: BookScan.scan
============================================================

Public signature (exact):

    public Map<String, List<Integer>> scan(List<String> lines, int wordLength);

Semantics:

- `lines` is the text split into lines, in original reading order.
  An empty list means an empty text. A `null` element is treated as "".
- `wordLength` is the target word length, measured by `strlen`.
  A negative or zero `wordLength` returns an empty map.
- A "word" inside a line is a maximal run of letters
  `[A-Za-z]` separated by any non-letter character (spaces,
  punctuation, digits, tabs, etc.). Apostrophes and hyphens are NOT
  part of a word.
- Case-insensitive matching: before any comparison, normalise both the
  candidate word and any stored key by applying `flipCase` consistently
  (e.g., normalise to lowercase by `flipCase`-ing if the char is upper,
  or just lowercase via `flipCase` semantics). Two words that differ
  only in case are the SAME key.
- Map keys are the normalised (lowercase) word strings.
- Map values are the 1-based line numbers in which the word appears,
  in ascending order, with one entry per *occurrence* (a word that
  appears twice on line 4 yields `[4, 4]`).
- Per-line occurrence counting MUST be done by calling `howManyTimes`
  with the normalised word as the substring inside the normalised line
  text (delimited so that adjacency does not produce false positives —
  see PART C).
- Words whose `strlen` differs from `wordLength` are skipped.

Worked example (input):

    lines      = ["The cat sat", "On the MAT", "the cat ran"]
    wordLength = 3

Expected return (key order does not matter):

    {
      "the": [1, 2, 3],
      "cat": [1, 3],
      "sat": [1],
      "mat": [2],
      "ran": [3]
    }

Note that "The", "the", and "THE" all collapse to key "the", and the
line list contains one entry per occurrence (line 2 contributes one
"the" even though it also contains "MAT").

============================================================
PART C — Non-functional requirements
============================================================

- Java 11 source compatibility. No external dependencies. Only
  java.util and java.lang imports.
- Class declaration: `public class BookScan { ... }` in the default
  package. No package declaration.
- Add this header at the very top of the file, unchanged (exact text,
  three lines):

  /*@Authors
  Student Names: <Kutay Murat Kasman><Furkan Bilal Yeşil><Ahmet Çavdar>
  Student IDs:<150210062><10210041><150210059>*/

- Use the three helper methods (howManyTimes, strlen, flipCase) as
  the ONLY way to count occurrences, measure length, and normalise
  case. Do not duplicate their logic inline. A reviewer will check
  that calls to these three methods appear in `scan`.
- When you delimit a normalised line for `howManyTimes`, ensure that
  searching for the substring "the" inside "thethem" does NOT match
  twice — use a delimiter character that cannot appear in a word
  (e.g. wrap each token with '\\u0001').
- Keep the file self-contained: one class, no inner classes unless
  strictly required.
- Do not print to stdout. The method returns the map; the caller
  decides what to do with it.

============================================================
PART D — Output format
============================================================

Return ONLY the contents of BookScan.java in a single fenced code
block. No prose, no markdown headings outside the code block.
```

**Rationale (each edit and the gap it closes).**

| Edit | Why it was added | Phase 1 / literature signal |
|---|---|---|
| Pinned API shape `Map<String,List<Integer>> scan(List<String>, int)` | Unmodified prompts leave the output type to the model; the four resulting variants would not be comparable. | Phase 1 Java/12 showed model-dependent output containers (`Optional`, lists). |
| Tokenisation rule (`[A-Za-z]` runs, no apostrophes/hyphens) | Without it, every model invents its own definition of "word" and the integration tests cannot agree. | Phase 1 Java/19 missed boundary cases because the prompt did not enumerate the digit-word vocabulary. |
| 1-based line numbers + per-occurrence repetition | Pins a concrete contract so the ECP/BVA table has a single ground truth. | TELPA result: LLMs cannot guess what they have not been told. |
| Explicit `flipCase`-as-normaliser rule | Forces a real call to `flipCase`; otherwise the model just pastes it and never uses it. | Phase 1 finding: helper methods get pasted but bypassed (Java/32 `poly` was the inverse pattern). |
| Explicit `howManyTimes` integration with delimiter wrapping | Eliminates the "thethem" false-positive class. This is exactly the kind of boundary the unmodified prompt would silently fail on. | Mirrors Phase 1 Java/0 exact-threshold boundary class. |
| Edge cases for `wordLength<=0`, empty lines, `null` element | Gives the ECP/BVA table its invalid/out-of-contract rows in advance. | ChatTester result: pre-specifying intention reduces compilation/assertion failures. |
| Java 11 source + no external deps | Matches the Phase 1 tooling already in `tools/`. | Phase 1 used Java 11 + plain main classes. |
| Worked example with expected return | Disambiguates the spec without leaking implementation. | HITS slicing motivation: concrete I/O examples drive coverage. |
| "Reviewer will check that the three helpers are called" | Strong nudge against the model inlining the helpers. | Pattern observed in Phase 1 base tests that flattened multi-method behaviour. |
| Single fenced code block, no prose | Makes the saved file directly committable without manual cleanup. | Pure operational reason. |

**Predicted improvements relative to Variant 1:**

- Both LLMs converge on the same `scan` signature, so the integration
  tests in Step 5 can be reused across variants with only minor edits.
- `flipCase` and `howManyTimes` are demonstrably called inside `scan`
  (greppable, will be checked in Step 4's smoke run).
- Tokenisation disagreements drop to zero, isolating remaining variance
  to genuine bugs (off-by-one in `howManyTimes`, missed delimiter
  wrapping, etc.) rather than spec misreadings.
