## Failure analysis (3 failures, all in `llm_b/unmodified`)

### F1. `testTokenisationCaseFoldingMatching` (Req 1)

```
expected: <3> but was: <2>
Requirement 1 failed: Tokenisation x case-folding x matching did not
find all mixed-case variations.
```

- Test input: `"The first line\nthe second line\nTHE third line"`, target length 3.
- Test expects `result.get("the").getTotalOccurrences() == 3`.
- Actual: 2. Trace: the unmodified Gemini BookScan counts
  `howManyTimes(line, "the") + howManyTimes(line, "THE")` per line —
  i.e., only the all-lowercase and all-uppercase forms. On line 1
  (`"The first line"`) neither pattern matches because `"The"` is
  MixedCase, contributing 0. Lines 2 and 3 contribute 1 each.
  `2 + 0 = 2`.
- **Root cause:** Class generation log Run 2 already recorded this as
  the MixedCase miss bug.
- **Predicted in Step 5?** Yes.

### F2. `testHowManyTimesSubstringOfLongerWord` (Req 5)

```
expected: <1> but was: <2>
Requirement 5 failed: howManyTimes x substring-of-longer-word
erroneously counted substrings inside longer words.
```

- Test input: `"cat concatenate"`, target length 3.
- Test expects `result.get("cat").getTotalOccurrences() == 1`.
- Actual: 2. Trace: `howManyTimes("cat concatenate", "cat")` matches at
  positions 0 and 4 (the second `cat` is inside `concatenate`), no
  word-boundary check.
- **Root cause:** Class generation log Run 2 already recorded this as
  the raw-substring-no-delimiter bug.
- **Predicted in Step 5?** Yes.

### F3. `testStrlenEmptyOneCharacterWords` (Req 6) — *not predicted*

```
expected: <1> but was: <2>
Requirement 6 failed: Incorrect occurrence count for 1-character word
'a'.
```

- Test input: `"I have a pen"`, target length 1.
- Test expects `result.get("a").getTotalOccurrences() == 1`.
- Actual: 2. Trace: `howManyTimes("I have a pen", "a")` matches both
  the standalone `"a"` at position 7 and the `"a"` inside `"have"` at
  position 3 — same substring-of-longer-word bug as F2, just exercised
  via a different word and length.
- **Root cause:** Identical to F2 (no word-boundary check in
  `howManyTimes` integration).
- **Why we missed it in Step 5:** we assumed only one of Gemini's tests
  would hit that bug. In fact two tests hit it because the test text
  happens to embed the target word `"a"` inside the longer word
  `"have"`. This is *stronger* evidence for the report — the bug
  surfaces in two independent test scenarios authored by the same
  agent, which is harder to dismiss as a one-off.

## Why the other three suites pass cleanly

- **`llm_a/unmodified` (GPT-5.5).** Step 5 noted GPT-5.5 read its own
  buggy source and wrote *regression* tests that ratify the bugs:
  e.g., Req 1 asserts three separate keys `"The"`/`"the"`/`"THE"` with
  count 1 each, which is exactly what the buggy BookScan returns. The
  suite passes because both sides share the same (flawed) view of
  correctness. The suite reveals **nothing** about whether the
  underlying integration is right — only that the suite agrees with
  its own source.
- **`llm_a/edited` and `llm_b/edited`.** Spec-compliant source + spec-
  aligned tests. All seven requirements pass for both LLMs.
