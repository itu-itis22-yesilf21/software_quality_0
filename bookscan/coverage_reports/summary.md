### Why the edited variants have *more* branches (and therefore a denominator effect)

The edited variants ship larger codebases:

- `llm_a/edited` has **60 branches** vs `llm_a/unmodified`'s 40 (+50 %)
  because GPT-5.5 added the `extractNormalisedWords`, `normalise`, and
  `isAsciiLetter` helpers plus the `U+0001`-delimiter handling. More
  code paths → larger denominator at the same numerator → lower
  percentage even though the suite covers more *absolute* logic.
- `llm_b/edited` has 44 branches vs `llm_b/unmodified`'s 40 (+10 %).
  Gemini added `normalizeToLowercase` but kept regex tokenisation, so
  the extra branch count is small.

Reading the percentages alone is therefore misleading. The right
metric for cross-variant comparison is *branches covered* per
*branches present*; the edited variants cover more behaviour at a
slightly lower percentage.

### Per-class breakdown (where coverage is missed)

| Variant | Class | Branch | Instr | Method |
|---|---|:-:|:-:|:-:|
| `llm_a/unmodified` | `BookScan`           | 84.21 % | 96.83 % | 100.00 % |
| `llm_a/unmodified` | `BookScan.WordInfo`  | 100.00 % | 84.78 % | 80.00 %  |
| `llm_b/unmodified` | `BookScan`           | 78.95 % | 92.92 % | 100.00 % |
| `llm_b/unmodified` | `BookScan.WordStats` | 50.00 % | 80.00 % | 71.43 %  |
| `llm_a/edited`     | `BookScan`           | 76.67 % | 93.54 % | 100.00 % |
| `llm_b/edited`     | `BookScan`           | 79.55 % | 92.75 % | 100.00 % |

The two unmodified variants' losses are concentrated in their
auto-generated inner-class plumbing:

- `WordInfo` (GPT) has unreachable `getCount/getLines/toString`
  paths — method coverage 80 % means one of `{ getCount, getLines,
  toString, addOccurrence, <init> }` was never called by the
  integration suite. Inspection of `BookScan.java`: `toString` is
  defined but never called by the test driver, since the driver uses
  `result.get("the").getCount()` and `getLines()` directly. So
  `toString` is the missed method.
- `WordStats` (Gemini) drops to 50 % branch coverage and 71.43 %
  method coverage; the missed branch is the `if (!this.lines.contains(lineNumber))`
  short-circuit in `addLine`, which only triggers on *re-adding* a
  line. Because the integration suite tests at most one match per
  line, that branch never runs. The missed method is `getWord()` —
  defined for completeness, never used by the test.

The two edited variants' losses are concentrated in `BookScan` itself:

- `llm_a/edited` (76.67 %) has 14 missed branches out of 60. The
  `normalise` helper has a per-character branch and the `extractNormalisedWords`
  trailing-word branch that the 7-test suite does not fully exercise.
- `llm_b/edited` (79.55 %) has 9 missed branches out of 44. The
  `normalizeToLowercase` helper's two-arm `if (Character.isUpperCase(c))`
  is only exercised by inputs that contain both upper- and lower-case
  characters; the `result.putIfAbsent` second arm only triggers on
  repeated words across different lines (the smoke suite hits this,
  but the integration suite mostly stays on single-line cases).

Step 9 (ECP/BVA) will translate these gaps into targeted mutation
tests, mirroring Phase 1's ImprovedBaseTest/BlackBoxTest pattern.

## Per-LLM and per-prompt aggregates

| Aggregation | Branch % | Branches covered | Branches total |
|---|:-:|---|---|
| GPT-5.5         (unmodified + edited) | (34 + 46) / (40 + 60) = **80.00 %** | 80 | 100 |
| Gemini 3.1 Pro  (unmodified + edited) | (31 + 35) / (40 + 44) = **78.57 %** | 66 |  84 |
| Unmodified+combined (LLM A + LLM B)   | (34 + 31) / (40 + 40) = **81.25 %** | 65 |  80 |
| Edited+combined     (LLM A + LLM B)   | (46 + 35) / (60 + 44) = **77.88 %** | 81 | 104 |

Interpretation:

- The two LLMs are within 1.4 percentage points of each other on
  weighted branch coverage. Coverage is not a strong LLM
  discriminator on this dataset.
- The unmodified variants score *higher* on the percentage than the
  edited variants, but they cover **fewer absolute branches** (65 vs
  81). The edited variants pay a denominator penalty for shipping
  more code, while actually exercising more behaviour. Once the
  Step 9 mutation tests close the remaining ECP gaps, the edited
  numbers will overtake the unmodified ones on both axes.

This mirrors the Phase 1 observation that **branch coverage on small
self-contained code is too easy to satisfy** and should not be used
on its own to compare LLM outputs.

## Comparison with Phase 1

| Cohort | Mean branch % | Notes |
|---|---|---|
| Phase 1 base suites (30 HumanEval tasks)       | 97.44 % | small single-method tasks |
| Phase 1 improved suites (30 HumanEval tasks)   | 99.87 % | after targeted ImprovedBaseTest additions |
| **Phase 2 integration suites (4 BookScan variants)** | **79.68 %** | larger multi-method class; ECP/BVA additions pending in Step 9 |

The 20-percentage-point drop is expected: BookScan is a multi-method
class whose `scan` integration touches three helpers, tokenisation,
case folding, delimiter wrapping, and several edge-case branches that
a 7-requirement test suite cannot saturate from a single sample text.
